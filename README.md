# WeatherDataWarehouse

A small analytical data warehouse for daily weather across 20 Indian cities. A Python loader pulls data from the free [Open-Meteo Archive API](https://open-meteo.com/en/docs/historical-weather-api) into DuckDB, and dbt Core models it into a tested star schema with monthly summaries and temperature anomaly detection.

The whole stack is free and runs on a laptop or in Google Colab. No API key is needed.

## Architecture

```
Open-Meteo Archive API
        |
        v
ingestion/fetch_weather.py      Python loader, retries, idempotent delete+insert, audit log
        |
        v
raw.weather_daily               one row per city per day, as returned by the API
raw.load_audit                  one row per city per run: rows loaded, status, error
        |
        v  dbt Core (dbt-duckdb)
staging.stg_weather_daily       typed, renamed, deduplicated (latest load wins)
        |
        v
marts.dim_city                  city, state, region, data coverage
marts.fct_daily_weather         daily facts + 7-day rolling average
marts.mart_city_monthly         monthly temperature, rainfall, humidity per city
marts.mart_temperature_anomalies  days far from the trailing 30-day baseline (z-score)
```

## Key design choices

- **Idempotent loads.** For each city the loader deletes the requested date range and inserts it again inside one transaction. Re-running a day never duplicates rows.
- **Audit trail.** Every run writes a row per city to `raw.load_audit`, so a failed city is visible without reading logs. One failing city does not stop the others.
- **Deduplication in staging.** `stg_weather_daily` keeps only the latest load for each city and day, so the marts stay correct even if raw data is loaded twice by other means.
- **Anomaly detection in SQL.** Each day's mean temperature is compared with the city's previous 30 days (the day itself is excluded). Days beyond 2.5 standard deviations are flagged as heat or cold anomalies. Both values are dbt variables in `dbt_project.yml`.
- **Data tests.** 27 dbt tests check uniqueness, nulls, accepted values, relationships and value ranges, using a custom `value_in_range` generic test. Python unit tests cover parsing, validation and idempotency.

## Project structure

```
config/cities.yml               20 cities with coordinates
ingestion/fetch_weather.py      API loader
scripts/make_sample_data.py     generates the offline sample in data/sample
data/sample/                    synthetic sample data for 5 cities (not real observations)
dbt/                            dbt project: sources, staging, marts, macros, tests
tests/                          pytest unit tests for the loader
weather_pipeline_colab.ipynb    end-to-end run in Google Colab
```

## Run it locally

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# Load the last 90 days for all 20 cities
python -m ingestion.fetch_weather --days 90

# Or load a fixed range
python -m ingestion.fetch_weather --start 2026-01-01 --end 2026-06-30

# Run the unit tests
python -m pytest -q

# Build and test the warehouse
cd dbt
dbt build --profiles-dir .
```

The DuckDB file is written to `warehouse/weather.duckdb`. Set `WEATHER_DB_PATH` to use a different location.

### Offline mode

Without internet access, load the bundled sample instead of calling the API:

```bash
python -m ingestion.fetch_weather --sample-dir data/sample
```

The sample is synthetic data in the Open-Meteo response format, generated by `scripts/make_sample_data.py`. It is only there so the pipeline and tests can run anywhere.

## Run it in Google Colab

Open `weather_pipeline_colab.ipynb` in Colab and choose Runtime > Run all. It clones the repo, loads the data, runs the tests, builds the dbt models and shows the results.

## Example queries

```sql
-- Hottest and wettest cities
select city, round(avg(avg_temp_c), 1) as avg_temp_c, sum(total_rain_mm) as rain_mm
from marts.mart_city_monthly
group by city
order by avg_temp_c desc;

-- Strongest temperature anomalies
select city, weather_date, temp_mean_c, baseline_mean_c, z_score, anomaly_type
from marts.mart_temperature_anomalies
order by abs(z_score) desc
limit 10;

-- Cities that failed in the latest run
select city, error_message
from raw.load_audit
where run_id = (select run_id from raw.load_audit order by loaded_at desc limit 1)
  and status = 'FAILED';
```
